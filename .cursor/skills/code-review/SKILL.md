# 代码审查（Code Review）

适用于任意语言/技术栈的结构化审查。根据范围调整深度：小改动快速过，PR 合并前完整过。

## 工作流程

1. **确定范围**
   - 优先看 `git diff` / PR diff，不要一上来通读全仓库。
   - 没有 diff 时：读用户指定的文件或模块。
   - 先弄清改动意图（修 bug / 新功能 / 重构），再评判设计是否合理。

2. **理解上下文**
   - 改动是否符合项目现有模式？
   - 有哪些不变量或契约必须保持？

3. **按清单审查**：使用 [checklist.md](checklist.md)。不适用的类别可跳过。

4. **能验证则验证**
   - 用户期望或 CI 可能失败时：跑针对性测试、lint 或构建。
   - **禁止**未执行却声称「测试已通过」。

5. **按下方模板输出报告**。

## 严重级别

| 级别 | 标签 | 含义 |
|------|------|------|
| P0 | **严重** | 明确 bug、安全问题、数据丢失或线上必挂 — **阻止合并** |
| P1 | **重要** | 高概率 bug、缺错误处理、明显违反分层/设计 — **应修复** |
| P2 | **次要** | 可读性、命名、小范围重构 — 可修或可跟进 |
| P3 | **建议** | 风格偏好 — 可选 |

每条 P0/P1 必须注明 **文件 + 位置**，并说明 **影响**。优先用代码引用，少空泛描述。

## 输出模板

```markdown
## 摘要
[1～3 句话：改了什么、整体风险]

## 审查意见

### P0 — 严重
- **[文件:行号]** 问题描述
  - 原因：…
  - 建议：…

### P1 — 重要
…

### P2 — 次要
…

### P3 — 建议
…

## 做得好的地方
- …

## 测试建议
- [ ] …
```

某级别无问题时**省略该节**。若完全无问题，明确写出，并仍提示潜在风险或缺失的测试。

## 审查原则

- **控制范围**：不要求改动范围外的顺手重构，除非影响正确性。
- **有据可依**：区分「确定是 bug」和「推测」；不确定的标为「待确认」。
- **尊重项目惯例**：命名、分层、模式与仓库一致，除非明显有害。
- **可执行**：每条意见给出具体改法，不只批评。
- **详略得当**：小改动简评；大 PR 必须谈架构与测试覆盖。

## 按场景的侧重点

| 用户意图 | 重点 |
|----------|------|
| 合并前 PR | 完整清单；先列 P0/P1 阻塞项 |
| 快速看一眼 | 正确性 + 安全 + 明显 bug |
| 偏安全 | 清单中安全项；密钥/鉴权/输入校验 |
| 纯重构 | 行为是否一致、回归风险、测试是否更新 |
| 偏架构 | 边界、依赖方向、耦合、扩展点 |

## Android / 移动端（仅相关时）

审查 Kotlin、Compose、Android 代码时额外关注：

- **生命周期**：`Context`、Flow 收集、回调在页面销毁后泄漏
- **线程**：主线程阻塞、共享可变状态的竞态
- **UI 状态**：单一数据源；导航/Toast 等副作用不在 UI 重复实现
- **模块化**：feature 边界、Hilt 依赖方向、禁止下层依赖上层实现
- **网络**：超时、错误路径、Token/401、登出与跳转顺序

## 禁止事项

- 没看 diff 就盖章通过
- 正确性/安全问题还没说完就先列风格意见
- 建议重写与本次无关的代码
- 无项目规范支撑的个人偏好当 P0/P1（应降为 P3）
